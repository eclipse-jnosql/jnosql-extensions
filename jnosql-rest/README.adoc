= Eclipse JNoSQL REST
:toc:

Optional extension that exposes Jakarta Data repositories as Jakarta REST resources. A JSR 269 annotation processor
generates readable Java source from Mustache templates at compile time; there is no runtime reflection.

This `1.x.x` backport targets Jakarta Data 1.0. Dynamic `Restriction<T>` search (Jakarta Data 1.1) is not available: no search endpoints, HTTP `QUERY` designator or search request DTOs are generated. Derived queries, `@Find`, `@Query`, count/exists methods, pagination, `Limit`, `Sort` and `Order` work as in the newer version.

== Modules

[cols="1,3"]
|===
|`jnosql-rest-api` |Public annotations: `@RestRepository`, `@RestExclude`, `@RestDTO`, `RestExposure`, `RestOperation`.
|`jnosql-rest-processor` |Annotation processor, generation model and Mustache templates.
|`jnosql-rest-tests` |Compilation, reflection, Weld/CDI and Mockito delegation tests.
|===

== Usage

[source,java]
----
@Repository
@RestRepository(path = "/products")
public interface ProductRepository extends CrudRepository<Product, UUID> {

    List<Product> findByCategory(String category);
}
----

The processor generates `ProductRepositoryResource` (`<RepositoryName>Resource`, same package) with `@Path`,
`@RequestScoped`, final dependency fields, a package-private no-argument constructor that sets every dependency to
`null`, and a public `@Inject` constructor.

Add the API as a dependency and the processor (and, for DTO mode, MapStruct) to the compiler `annotationProcessorPaths`.
Adding the MapStruct annotation artifact alone does not activate its processor:

[source,xml]
----
<annotationProcessorPaths>
    <path><groupId>org.eclipse.jnosql.rest</groupId><artifactId>jnosql-rest-processor</artifactId></path>
    <path><groupId>org.mapstruct</groupId><artifactId>mapstruct-processor</artifactId></path>
</annotationProcessorPaths>
----

== Exposure

Adding `@RestRepository` is enough; use standard Jakarta REST annotations only to customize.

[cols="1,1,1,1"]
|===
|Policy |Ordinary method |Method with `@Path` |Method with `@RestExclude`

|`ALL` (default) |Exposed |Exposed with the custom path |Excluded
|`EXPLICIT` |Excluded |Exposed with the custom path |Excluded
|`NONE` |Excluded |Excluded |Excluded
|===

* `@Path("")` (or `@Path("/")`) explicitly exposes the collection root, also under `EXPLICIT`.
* `@RestExclude` always wins; `@Path` never bypasses it, and `NONE` ignores `@Path`.
* Mutating declared methods (`deleteBy*`, `@Delete` without an entity, `@Query` DELETE/UPDATE) are published
only with a method-level `@Path`, even under `ALL`.
* `@RestRepository(exclude = ...)` removes operation categories. A `@Path` on a method of an excluded category is a
compile error.

== Routing

Precedence: explicit `@Path`, then a recognized canonical operation, then `GET|POST /<methodName>`.
A declared `@Path` replaces the route entirely: the method name is never appended.

[source,java]
----
@Repository
@RestRepository(path = "/products")
public interface ProductRepository extends BasicRepository<Product, UUID> {

    @Find
    List<Product> findByCategory(String category);               // GET /products/findByCategory?category=books

    @Find
    List<Product> find(String category, BigDecimal price);       // GET /products/find?category=books&price=100

    @Find
    @Path("/by-category")
    List<Product> findByName(String name);                       // GET /products/by-category?name=...

    @Find
    @Path("/{category}")
    List<Product> find(String category, BigDecimal price);       // GET /products/books?price=100
}
----

Canonical routes are chosen from the repository's operation metadata, not from method names:

[cols="1,2"]
|===
|Entity insertion |`POST /`
|Entity update |`PUT /` (or `PUT /{id}` in DTO mode)
|Primary-key lookup |`GET /{identifier}`
|Primary-key deletion |`DELETE /{identifier}`
|Paginated `findAll` |`GET /`
|Any other finder |`GET /{methodName}`
|`save`, entity `delete` |`PUT /save`, `DELETE /delete`
|===

The identifier variable is the entity's `@Id` attribute (`/{cnpj}` for a `Company` identified by `cnpj`). A custom
`@Find` or `@Delete` is routed by identifier only when it is proven to use the primary key: a single parameter of the
identifier type bound with `@By("id(this)")`, `@By` on the identifier attribute, or a parameter named after it, or a
`findBy<Id>`/`deleteBy<Id>` name. Otherwise the method-based route is used.

=== Parameter binding

1. Explicit `@PathParam` or `@QueryParam`; the HTTP name is the annotation value.
2. A Java parameter named like a URI template variable becomes a `@PathParam`.
3. Every other scalar parameter becomes a `@QueryParam` named after the Java parameter.

`PageRequest`, `Limit`, `Sort` and `Order` keep their dedicated handling, and entity parameters stay
request bodies. Jakarta Data `@By` is independent: it selects the attribute, never the HTTP name or location. A
MicroProfile OpenAPI `@Parameter(in = ...)` contradicting the real location is a compile error.

=== Compile-time validation

The build fails on: invalid URI templates, repeated variables, template variables without a parameter, `@PathParam`
outside the template, `@QueryParam` naming a path variable, both annotations on one parameter, other Jakarta REST
binding annotations (`@HeaderParam`, `@BeanParam`, ...), repeated query names, collection parameters bound to the
path, path variables on body operations, and routes with the same HTTP method and structurally equivalent template
(`/{id}` and `/{category}` collide; routes differing only by query parameters or overloads collide too). Different HTTP
methods on one route are valid.

== Migration

`@RestExpose` was removed (source-incompatible; no deprecation).

[cols="1,1"]
|===
|Before |After
|`@RestExpose(path = "/x")` |`@Path("/x")`
|bare `@RestExpose` on an ordinary method |nothing under `ALL`; `@Path("/x")` under `EXPLICIT`
|bare `@RestExpose` on a mutating query |`@Path("/purge")`
|`POST /insert`, `PUT` update |`POST /`, `PUT /`
|`GET /findById?id=1`-style inherited lookups |`GET /{id}`
|===

== Repository types

Capabilities come from the methods the repository actually declares or inherits, never from interface names.
`CrudRepository`, `BasicRepository` (no `insert`/`update`) and plain `@Repository` interfaces are supported; for the
latter the entity is inferred from the return types and parameters of the methods, which must agree on one entity, and
no CRUD operation is invented. Methods inherited from intermediate interfaces are included.

== DTOs

`@RestDTO` generates `<Entity>DTO`, `<Entity>CreateRequest`, `<Entity>UpdateRequest` records and a
`<Entity>DTOMapper` interface annotated `@Mapper(componentModel = MappingConstants.ComponentModel.JAKARTA_CDI, unmappedTargetPolicy = ReportingPolicy.IGNORE)`; MapStruct generates the
implementation and the resource receives the mapper through constructor injection. Developer-defined types with those
names are reused (and validated), never overwritten.

* Three attributes control which entity attributes the generated DTOs carry. They affect only the generated REST
DTOs, never the database model or persistence:
+
[cols="2,2,2"]
|===
|Attribute |Request DTOs (create and update) |Response DTO

|`exclude` |removed |removed
|`excludeFromRequest` |removed |kept
|`excludeFromResponse` |kept |removed
|===
+
Request exclusions are `exclude` plus `excludeFromRequest`; response exclusions are `exclude` plus
`excludeFromResponse`. Other attributes are mapped normally. Repeated names are ignored and unknown names are
compilation errors; excluding every attribute from requests is also an error. The identifier stays available to
repository operations and path parameters even when excluded from requests. Attributes excluded from responses
are also not sortable.
+
[source,java]
----
@RestDTO(
    exclude = {"internalNotes"},
    excludeFromRequest = {"id"},
    excludeFromResponse = {"supplier", "supplierCost"}
)
----
+
[cols="2,1,1"]
|===
|Attribute |Request DTO |Response DTO

|`id` |excluded |included
|`name`, `price` |included |included
|`supplier`, `supplierCost` |included (mapped into the entity) |excluded
|`internalNotes` |excluded |excluded
|===
+
*Behavior change:* `exclude` used to affect only the response DTO, so excluded attributes remained writable through
create and update requests. It now removes them from requests too; use `excludeFromResponse` to keep the previous
behavior.
* Update requests use `NullValuePropertyMappingStrategy.IGNORE`: `null` means "unchanged". There is no presence-aware
(absent vs. explicit `null`) patch.
* Nested beans become `<Simple>DTO`; `Optional` getters are unwrapped; recursive, generic or abstract nested types are
compile errors.
* Record entities cannot be updated in place; no update endpoint is generated for them.

=== Entity construction patterns

Object construction is delegated to MapStruct (see the
https://mapstruct.org/documentation/stable/reference/html/[MapStruct reference guide]); the extension adds no mapping
validation of its own. Entities without setters use every readable attribute in the create request. Verified by tests
with the real processors and compiled mappers:

[cols="2,3"]
|===
|Pattern |Result

|Mutable JavaBean (no-arg constructor, setters) |Supported, including nested `@Embeddable` records.
|Immutable class with an accessible constructor |Supported (create and response mapping).
|Java record |Supported through the canonical constructor; no setters or getters needed.
|Builder (`builder()`/`build()`) |Supported; no public no-arg constructor required.
|Builder with other names (`newBuilder()`/`create()`) |Supported; detected by MapStruct.
|Private constructor with a static factory (`of(...)`) |Not supported: MapStruct reports that there is no accessible
constructor. Add a builder to the entity.
|===

Immutable entities, including records, have no generated update endpoint because updates map onto an existing instance.
`@ObjectFactory` and custom `BuilderProvider` SPI configuration were not verified.

==== Member visibility

Java accessibility does not make a member a MapStruct property. With MapStruct's default configuration, verified by
compiling real mappers and asserting the copied values (mapper in the entity's package and in another package, with the
same result), only `public` members are mapped:

* `public` getter: read (entity to DTO). `public` setter: written (request to entity). `public` field: both.
* Package-private, protected or private getters, setters and fields are ignored by MapStruct, even when the mapper is in
the same package.

The REST processor discovers DTO attributes with the same rule, so a DTO is generated exactly when MapStruct can read
the attributes. An entity without any public getter, public field or record component is rejected with
"has no readable attributes" instead of producing an empty mapper; make the accessors public. A public getter paired
with a non-public setter maps the response only: the create request is built, but MapStruct cannot populate the entity
from it.

== Pagination

A method with one `PageRequest` parameter and a `Page<T>` or `CursoredPage<T>` return is published as a `GET`
endpoint. JNoSQL REST only translates HTTP input into a `PageRequest` and adapts the result;
the Jakarta Data provider runs the query and decides the page boundaries. Nothing is paginated in memory and a
provider `UnsupportedOperationException` (for example no cursor support) is propagated, never turned into offset
paging. A `PageRequest` without a page return, or a page return without a `PageRequest`, is rejected like any other
unsupported signature. Business parameters named `offset`, `size`, `includeTotal` or `cursor` clash with the
pagination parameters and are errors.

All pagination parameters are received as strings so that invalid values answer `400 Bad Request` rather than the
`404` Jakarta REST uses for failed conversions. `size` defaults to `20` and is limited to `1..100`.

=== Offset pagination (`Page<T>`)

[source,java]
----
@Find
Page<Product> findByCategory(String category, PageRequest pageRequest);
----

[source,http]
----
GET /products/findByCategory?category=books&offset=0&size=20&includeTotal=true
----

* `offset` is the zero-based *page* offset, not a row offset: `0` is the first page, `1` the second. It becomes
`PageRequest.ofPage(offset + 1, size, includeTotal)`. Default `0`; negative or overflowing values are rejected.
* `includeTotal` defaults to `false`, so no count query is requested unless the client asks for it. When it is `false`
(or the provider does not supply totals) the generated code never calls `totalElements()`/`totalPages()`.

[source,json]
----
{ "content": [ { "id": "123", "name": "Notebook" } ], "offset": 0, "size": 20, "hasNext": true,
  "hasPrevious": false, "totalElements": 145, "totalPages": 8 }
----

`totalElements` and `totalPages` are `null` when totals are not available. The response is the reusable
`org.eclipse.jnosql.rest.pagination.PageResponse` record; no per-repository response class is generated.

=== Cursor pagination (`CursoredPage<T>`)

[source,java]
----
@Find
@OrderBy("name")
@OrderBy("id")
CursoredPage<Product> findByCategory(String category, PageRequest pageRequest);
----

[source,http]
----
GET /products/findByCategory?category=books&size=20
GET /products/findByCategory?category=books&size=20&cursor=<nextCursor or previousCursor>
----

[source,json]
----
{ "content": [ ... ], "size": 20, "hasNext": true, "hasPrevious": false,
  "nextCursor": "djE7TjsuLi4", "previousCursor": null }
----

* Omit `cursor` for the first page. Follow `nextCursor` for the next page and `previousCursor` for the previous one;
each is present only when `hasNext()`/`hasPrevious()` is true, and the navigation methods of the page are not called
otherwise (`afterCursor` for next, `beforeCursor` for previous). Cursor responses carry no totals and no page numbers.
* *Ordering is mandatory and checked at compile time.* A cursor needs a total order, so the method must declare
`@OrderBy` attributes (or `OrderBy` in the method name, or `ORDER BY` in a `@Query`) that include the entity identifier,
the only attribute the processor can prove unique. Without it the method is skipped with a warning, or fails the build
when it carries `@Path`.
* Treat `cursor` as opaque. It is `v1;N|P;<query hash>;<typed keys>` encoded as Base64URL (no padding, at most 1024
characters and 8 keys). Key types: `String`, the integer and floating point types, `Boolean`, `BigDecimal`,
`BigInteger`, `UUID` and the `java.time` `LocalDate`, `LocalDateTime`, `LocalTime`, `Instant`; other key types fail
when the token is issued. No Java serialization or reflection is involved.
* A token is bound to the repository method and to its business parameters; using it
with another query answers `400`. The page size is not part of the binding and may change between requests.
Malformed, oversized, unversioned or unsupported-version tokens answer `400`.
* *Security:* tokens are neither signed nor encrypted. They reveal the sort-key values of the boundary row and can be
forged by a client, which only lets it start from another position of the same query; they do not widen access. Do not
rely on them for authorization, and put sensitive data out of sort keys. Tokens carry no expiry; whether a stale
cursor still works is a provider matter.

=== DTOs and OpenAPI

With `@RestDTO` the page content is mapped through the existing MapStruct mapper, so excluded attributes never reach
the response; the pagination metadata is added separately and never goes through the mapper. When MicroProfile OpenAPI
is on the classpath the pagination query parameters get an `@Parameter` description and the response schemas
(`PageResponse`, `CursorPageResponse`, the generated DTOs) are discovered by the implementation. Add `@APIResponse` for
`400` on the repository if you want it documented, and customize further with `META-INF/openapi.yaml` or an
`OASFilter`. No OpenAPI types are required otherwise.

== Collection root

`GET /products` is served by the inherited `findAll(PageRequest, Order<T>)` of `BasicRepository` (and so
`CrudRepository`), which returns a `Page<T>`. It is always bounded:

[source,http]
----
GET /products?offset=0&size=20&sort=name:asc,price:desc
----

* `offset` is the zero-based page offset (default `0`), `size` defaults to `20` and is limited to `1..100`,
`includeTotal` defaults to `false` (no count query). The response is the `PageResponse` described above; with
`@RestDTO` the content is mapped to the DTO.
* The inherited unbounded `findAll()`, including one redeclared with `@Override`, is never exposed, so there is no
second root route and nothing is paginated or sorted in memory. A repository without a paginated `findAll` gets no
collection root.
* A custom `findAll` that does not override a standard operation follows the ordinary custom-method conventions:
`@Find List<Product> findAll();` is served as `GET /products/findAll`, and `@Find @Path("/all")` moves it to
`GET /products/all`. JNoSQL also resolves an unannotated `findAll()` by name, so it is exposed the same way; prefer
`@Find`, which is the portable Jakarta Data declaration. It is the developer's own unbounded query, and it never
replaces the collection root.
* Invalid `offset`, `size` or `sort` values answer `400 Bad Request` before the repository is called.

== Limit

A method with a `Limit` parameter (and no `PageRequest`, no page return type) gets `limit` and `startAt` query
parameters:

[source,http]
----
GET /products/findByCategory?category=books&limit=10&startAt=5
----

`limit` is the maximum number of results (default `20`, maximum `100`); `startAt` is the one-based position of the
first result (default `1`) as defined by Jakarta Data `Limit`. Non-numeric, overflowing, zero or negative values and
`startAt < 1` answer `400`. `Limit` cannot be combined with `PageRequest` or a `Page` return; such a signature is
rejected at compile time. The limit is applied by the provider.

== Sort and Order

A method with a `Sort<Entity>` (one criterion) or `Order<Entity>` (several) parameter gets a `sort` query parameter:

[source,http]
----
GET /products/findByCategory?category=books&sort=price:desc
GET /products/findByCategory?category=books&sort=name:asc,price:desc
----

* Syntax: `attribute[:asc|:desc]` terms separated by commas; the direction is case-insensitive and defaults to `asc`;
the order of terms is preserved. A `Sort` accepts exactly one term; an `Order` accepts several and may be empty.
* The allowed attributes are generated at compile time from the entity (scalar attributes only; nested attributes are
rejected) minus `@RestDTO` exclusions, and, when a developer-defined DTO is visible, only the attributes that DTO
declares. `GET /products?sort=internalCode:asc` therefore answers `400` when `internalCode` is excluded. Sorting is
still done by the provider on the entity attribute.
* Unknown attributes, repeated attributes, invalid directions and malformed terms answer `400`.
* A `Sort<X>` or `Order<X>` whose type argument is not the repository entity is a compile error.
* Offset pagination: combine freely, `GET /products/findByCategory?category=books&offset=1&size=10&sort=name:asc`.
* Cursor pagination: a method with an `Order<Entity>` parameter and a `CursoredPage` return needs a total order, so
the client's `sort` must include the identifier (`sort=name:asc,id:asc`), otherwise `400`. The cursor is bound to the
sort (it is part of the existing token binding), so changing `sort` while following a cursor answers `400`. A static
`@OrderBy` (not combined with `Order`) is still required to include the identifier. No identifier is appended
silently.

Provider limits: whether dynamic `Order`/`Sort` and cursor pagination work depends on the Jakarta Data provider; its
`UnsupportedOperationException` is propagated.

== MicroProfile OpenAPI (optional)

When `org.eclipse.microprofile.openapi` is on the compile classpath, `@Tag`, `@SecurityRequirement` (type level),
`@Operation`, `@APIResponse(s)`, `@Tag`, `@SecurityRequirement`, `@Parameter` (method/parameter level) found on the
repository are copied to the generated resource. Without it, no OpenAPI import or annotation is generated.
Schemas are inferred by MicroProfile OpenAPI from generated DTOs. Customize with `META-INF/openapi.yaml` or an
`OASFilter`, following the merge rules of the MicroProfile OpenAPI specification. `@SecurityRequirement` documents but
does not enforce security.

Generated pagination parameters (`offset`, `size`, `includeTotal`, `limit`, `startAt`) are documented with their
OpenAPI types, bounds and defaults (for example `size`: integer, 1..100, default 20); the Java parameters stay
`String`, so runtime validation is unchanged. Generated creation operations document the `201` response with an
`application/json` schema: the generated response DTO when one exists, otherwise the entity. A repository `@APIResponse(responseCode = "201")` without content keeps its description and gets the schema;
any other declared `@APIResponse` takes precedence. Without MicroProfile OpenAPI on the compile classpath no OpenAPI
annotation is generated and the endpoints behave identically. Only generator output was tested; no OpenAPI implementation ran.

== CDI, CDI Lite and discovery

Constructor injection only. The package-private constructor exists for proxying; it is deliberately not public. A
Jakarta REST runtime that requires a public no-argument constructor for `@RequestScoped` resources is a known
limitation. CDI discovery does not by itself register resources: Jakarta REST runtimes need either an
`Application` subclass (scanning) or `@ApplicationPath` plus bean-discovery of the generated package.

== Known limitations

* `Limit`, `Sort<T>`, `Order<T>` and the paginated root `findAll` are supported, see <<Collection root>>,
<<Limit>> and <<Sort and Order>>. The inherited unbounded `findAll()` is deliberately never exposed.
* Custom-DTO sort surface is derived only when the developer's DTO type is visible to the processor; otherwise the
entity attributes minus `@RestDTO` exclusions apply. See <<Pagination>> for the other limits of paging.
* No dynamic `Restriction<T>` search (requires Jakarta Data 1.1); methods taking it are not supported.
* Bulk operations (`saveAll`, `insertAll`, `updateAll`, `deleteAll`) are not generated.
* No Bean Validation integration, no CDI Lite runtime test.
